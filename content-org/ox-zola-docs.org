#+begin_description
An Org exporter backend for writing Zola posts in Org mode.
#+end_description

Ox-Zola is an Org export backend that writes Markdown with TOML front matter for the Zola static site generator. It supports subtree and whole-file exports, Org tags as taxonomies, Zola internal links, page bundles, and Zola 0.23 components.

*** What it handles

Exports support files, subtrees, and whole-file WIM exports. Org tags create categories and tags, file-level ~zola_categories~ and ~zola_tags~ keywords set taxonomies directly, and page bundles are configured through export properties.

Point ~ox-zola-base-dir~ at the site and set the default section. Start with [[/projects/ox-zola/getting-started/][Getting Started]], then use the reference pages for links, components, and migration.

*** Requirements

Ox-Zola requires Emacs 27.2 or newer and a Zola site.

*** Install

Ox-Zola is available on [[https://melpa.org/#/ox-zola][MELPA]]. With MELPA configured:

#+begin_src text
M-x package-install RET ox-zola RET
#+end_src

Or with ~use-package~:

#+begin_src elisp
(use-package ox-zola
  :ensure t)
#+end_src

The ox-hugo dependency is installed automatically. If MELPA is not configured yet, see the [[https://melpa.org/#/getting-started][MELPA getting-started guide]]. For alternative installation methods, see [[/projects/ox-zola/getting-started/installation/][Installation]].

*** Configure

Point ox-zola at the Zola site and choose a default section:

#+begin_src elisp
(setq ox-zola-base-dir "~/my-zola-site")
(setq ox-zola-section "posts")
#+end_src

The same values can be set per file:

#+begin_src org
,#+zola_base_dir: /path/to/your/zola/project
,#+zola_section: posts
#+end_src

*** Write and export a post

Write a post as an Org heading:

#+begin_src org
,* My First Post
:PROPERTIES:
:EXPORT_FILE_NAME: my-first-post
:END:
This is my first post written in Org mode.
#+end_src

Export with ~M-x org-export-dispatch~ (~C-c C-e~). The Zola backend appears under ~Z~:

#+begin_src text
 [Z] Export to Zola Markdown
     [z] Subtree or File to Md file
     [Z] File to a temporary Md buffer
     [O] Subtree or File to Md file and open
     [f] File to Md file
     [A] All subtrees (or File) to Md file(s)
     [o] File to Md file and open
#+end_src

*** Taxonomies

Use Org tags:

#+begin_src org
,* My First Post :@blogging:emacs:
#+end_src

This creates a category ~blogging~ and a tag ~emacs~. File-level keywords work too:

#+begin_src org
,#+zola_categories: blogging
,#+zola_tags: emacs org-mode
#+end_src

Both produce Zola front matter:

#+begin_src toml
[taxonomies]
categories = ["blogging"]
tags = ["emacs", "org-mode"]
#+end_src

*** Page bundles

Put a post and its assets in the same directory by exporting an ~index~ file:

#+begin_src org
,* My First Post :@blogging:emacs:
:PROPERTIES:
:EXPORT_ZOLA_SECTION: posts/my-first-post
:EXPORT_FILE_NAME: index
:END:
#+end_src

*** Requirements

Ox-Zola requires Emacs 27.2 or newer. It depends on [[https://github.com/kaushalmodi/ox-hugo][ox-hugo]], which is installed as a package dependency. You also need a Zola site to export into.

*** Install from MELPA

Ox-Zola is available on [[https://melpa.org/#/ox-zola][MELPA]]. With MELPA configured, install it with:

#+begin_src text
M-x package-install RET ox-zola RET
#+end_src

Or with ~use-package~:

#+begin_src elisp
(use-package ox-zola
  :ensure t)
#+end_src

The ox-hugo dependency is installed automatically. If MELPA is not configured yet, see the [[https://melpa.org/#/getting-started][MELPA getting-started guide]].

*** Alternative installations

With ~straight.el~:

#+begin_src elisp
(use-package ox-zola
  :straight (:host github :repo "gicrisf/ox-zola"))
#+end_src

With Emacs 29's built-in ~:vc~:

#+begin_src elisp
(use-package ox-zola
  :vc (:url "https://github.com/gicrisf/ox-zola"

#+end_src

#+begin_src elisp
(with-eval-after-load 'ox

#+end_src

#+end_description

*** Before you export

Set ~ox-zola-base-dir~ or the ~ZOLA_BASE_DIR~ keyword. Set ~ox-zola-section~ or the matching section keyword for the default output section.

For subtree exports, the post subtree must have ~EXPORT_FILE_NAME~. A subtree with ~EXPORT_FILE_NAME~ cannot contain another subtree with that property; post subtrees are leaves.

*** Export commands

The Zola backend is available under ~Z~ in ~M-x org-export-dispatch~ (~C-c C-e~):

| Key | Action |
| ~z~ | Export the current subtree or file |
| ~O~ | Export the current subtree or file and open it |
| ~A~ | Export all subtrees, or the whole file |
| ~Z~ | Export the file to a temporary buffer |
| ~f~ | Export the file to a Markdown file |
| ~o~ | Export the file to a Markdown file and open it |

The subtree/file command is the usual WIM export: if point is in a valid post subtree it exports that subtree; otherwise, if the file has a ~#+title~, it exports the whole file.

*** Customization

Use ~M-x customize-group RET ox-zola~ to inspect the available export options.

#+begin_description
Choose between one post per subtree and one post per file.
#+end_description

There are two main flows for writing with ox-zola.

*** One post per Org subtree

This is the preferred workflow. Each post is a subtree with ~EXPORT_FILE_NAME~, and you can either export the current subtree or all valid post subtrees at once.

Subtree exports let you use Org's tag and property inheritance, TODO states for draft status, automatic weight calculation, and shared file-level configuration.

*** One post per Org file

This also works, but a whole-file export cannot take advantage of subtree inheritance or automatic weights and taxonomies. Metadata that would normally be inherited must be written explicitly with file-level keywords.

For a first post, see [[/projects/ox-zola/getting-started/quick-start/][Quick Start]]. For Hugo migration details, see [[/projects/ox-zola/getting-started/migration-from-ox-hugo/][Migrating from ox-hugo]].

*** Quick start

1. Install ox-zola alongside ox-hugo.
2. Change the export command from ~org-hugo-export-*~ to ~ox-zola-export-*~.
3. Export your posts. Most Org files need no changes.

#+begin_src elisp

(org-hugo-export-wim-to-md)

;; After, with ox-zola
(ox-zola-export-wim-to-md)
#+end_src

*** Keywords

Both ~HUGO_*~ and ~ZOLA_*~ keywords are recognized. You can keep existing keywords or migrate gradually:

#+begin_src org
;; These are equivalent
,#+hugo_base_dir: ~/myblog
,#+zola_base_dir: ~/myblog

,#+hugo_section: posts
,#+zola_section: posts

,#+hugo_tags: emacs org-mode
,#+zola_tags: emacs org-mode
#+end_src

*** Subtree properties

Both Hugo-named and Zola-named properties are accepted. New files should use the Zola names:

| Hugo property | Zola property |
| ~EXPORT_HUGO_SECTION~ | ~EXPORT_ZOLA_SECTION~ |
| ~EXPORT_HUGO_SECTION_FRAG~ | ~EXPORT_ZOLA_SECTION_FRAG~ |
| ~EXPORT_HUGO_BUNDLE~ | ~EXPORT_ZOLA_BUNDLE~ |
| ~EXPORT_HUGO_TAGS~ | ~EXPORT_ZOLA_TAGS~ |
| ~EXPORT_HUGO_CATEGORIES~ | ~EXPORT_ZOLA_CATEGORIES~ |
| ~EXPORT_HUGO_WEIGHT~ | ~EXPORT_ZOLA_WEIGHT~ |
| ~EXPORT_HUGO_LAYOUT~ | ~EXPORT_ZOLA_TEMPLATE~ |
| ~EXPORT_HUGO_AUTO_SET_LASTMOD~ | ~EXPORT_ZOLA_AUTO_SET_LASTMOD~ |

Additional Zola-named keywords include ~ZOLA_AUTO_SET_LASTMOD~, ~ZOLA_USE_CODE_FOR_KBD~, ~ZOLA_PREFER_HYPHEN_IN_TAGS~, ~ZOLA_ALLOW_SPACES_IN_TAGS~, ~ZOLA_BUNDLE~, ~ZOLA_DATE_FORMAT~, ~ZOLA_LEVEL_OFFSET~, ~ZOLA_CUSTOM_FRONT_MATTER~, and ~ZOLA_FRONT_MATTER_KEY_REPLACE~.

*** Subtree and file export

The WIM export detects whether to export the current subtree or the whole file.

*** Front matter transformations

Ox-Zola converts Hugo-specific front matter to Zola's shape:

| Hugo | Zola | Notes |
| ~lastmod~ | ~updated~ | Renamed |
| ~layout~ | ~template~ | Renamed |
| ~tags: [...]~ | ~[taxonomies]~ | Restructured |
| ~categories: [...]~ | ~[taxonomies]~ | Restructured |
| ~menu~, ~resources~, ~outputs~ | removed | Zola does not use them |

Example:

#+begin_src toml
# Hugo front matter
+++
title = "My Post"
tags = ["emacs", "org"]
categories = ["tutorials"]
lastmod = 2024-01-15
layout = "post"
+++
#+end_src

#+begin_src toml
# Zola front matter
+++
title = "My Post"
updated = 2024-01-15
template = "post.html"

[taxonomies]
tags = ["emacs", "org"]
categories = ["tutorials"]
+++
#+end_src

*** Internal links

Hugo's ~relref~ shortcode is replaced with Zola's ~@/~ path syntax:

#+begin_src markdown
# Hugo output
[other post]({{< relref "other.md" >}})
[heading]({{< relref "post.md#section" >}})

# Zola output
[other post](@/posts/other.md)
[heading](@/posts/post.md#section)
#+end_src

*** Shortcodes and components

Hugo shortcodes do not map directly to Zola 0.23 components. Convert each one manually.

#+begin_src markdown
# Hugo paired shortcode
{{< quote >}}
Content here
{{< /quote >}}

# Zola 0.22 legacy shortcode syntax
{% quote() %}
Content here
{% end %}

# Zola 0.23 component call
{% <site.quote> %}
Content here
{% </site.quote> %}
#+end_src

#+begin_src markdown
# Hugo inline shortcode
{{< youtube abc123 >}}

# Zola 0.22 legacy shortcode syntax
{{ youtube(id="abc123") }}

# Zola 0.23 component call
{{<site.youtube id="abc123" />}}
#+end_src

If you still target Zola 0.22, ox-zola can emit the legacy shortcode syntax for Org special blocks. For 0.23 and newer, define and call Tera components instead. See [[/projects/ox-zola/content/components/][Components and Special Blocks]].

*** Figures

For Zola 0.23 and newer, use a figure component or plain HTML:

#+begin_src html
<figure>
  <img src="/images/diagram.png" alt="Diagram">
  <figcaption>A caption</figcaption>
</figure>
#+end_src

The old Hugo and Zola shortcode forms are for legacy Zola versions only.

*** Page bundles

Hugo and Zola differ in page bundle conventions:

| Hugo | Zola |
| ~content/posts/my-post/index.md~ | ~content/posts/my-post/index.md~ |
| Leaf bundle | Section with ~_index.md~ or a page |
| ~resources~ front matter | Co-located assets |

Simple bundles containing a post and images work similarly. Complex Hugo bundles with resource processing need manual adjustment.

*** Manual changes

- Replace Hugo-specific export snippets with HTML or component calls.
- Rewrite custom Hugo shortcodes as Tera components.
- Remove Hugo menu configuration; Zola navigation lives in the template configuration instead.

*** Menus

Hugo's menu system does not exist in Zola. Remove ~#+hugo_menu~ entries and configure navigation in ~config.toml~ or the site templates.

#+end_description

*** Mixed line endings

If an Org file contains a mix of Unix (~\n~) and DOS/Windows (~\r\n~) line endings, the exported Markdown can lose paragraph breaks. This can happen when an attached file, such as an SVG, was created outside Emacs with different line endings.

Make the line endings consistent in the source file, or align the export coding system with your buffer:

#+begin_src elisp
(setq org-export-coding-system 'utf-8-unix)
#+end_src

If you need to override it only during export:

#+begin_src elisp
(defun my/ox-zola-always-utf-8-unix (orig-fun &rest args)
  (let ((org-export-coding-system 'utf-8-unix))
    (apply orig-fun args)))

(with-eval-after-load 'ox-zola
  (advice-add 'ox-zola-export-to-md :around #'my/ox-zola-always-utf-8-unix))
#+end_src

*** Missing output or metadata

Check that:

- ~ox-zola-base-dir~ points at the Zola site root.
- The section or ~EXPORT_FILE_NAME~ is set correctly.
- A subtree export has ~EXPORT_FILE_NAME~ and does not nest another post subtree.
- The exported Markdown passes ~zola check~.

*** Subtree exports

For subtree exports, the post heading and its property drawer provide most front matter values:

| Zola field | Org source |
| ~title~ | Subtree heading |
| ~date~ | ~CLOSED~ property or ~EXPORT_DATE~ |
| ~updated~ | ~ZOLA_UPDATED~ keyword, ~:LOGBOOK:~ history, or automatic tracking |
| ~draft~ | ~TODO~ state or ~ZOLA_DRAFT~ keyword |
| ~weight~ | ~EXPORT_ZOLA_WEIGHT~ |
| ~taxonomies.tags~ | Subtree tags without ~@~ |
| ~taxonomies.categories~ | Subtree tags with ~@~ |
| ~path~ / output file | ~EXPORT_FILE_NAME~, section, and bundle properties |

Zola uses TOML front matter.

*** File exports

For whole-file exports, use file-level keywords:

#+begin_src org
,#+title: My Post
,#+date: 2026-10-31
,#+zola_tags: emacs org-mode
,#+zola_categories: blogging
#+end_src

Legacy ~HUGO_*~ keywords remain accepted; see [[/projects/ox-zola/getting-started/migration-from-ox-hugo/][Migrating from ox-hugo]] for compatibility details.

*** Precedence

Dates are resolved in this order:

1. The first transition to a ~DONE~ state in the ~:LOGBOOK:~ drawer
2. The ~CLOSED~ property
3. ~EXPORT_DATE~
4. The ~#+date:~ keyword

~updated~ follows the ~:LOGBOOK:~ history when available, then automatic last-modified tracking, then an explicit ~ZOLA_UPDATED~ keyword.

Fields that are not part of Zola's front matter (~publishDate~, ~expiryDate~, ~menu~, ~resources~) are not emitted.

#+begin_description
Set post dates and updated timestamps from Org.
#+end_description

*** Date formats

Date properties accept RFC3339 date-times or ordinary Org timestamps:

#+begin_src org
:EXPORT_DATE: 2026-10-31
:EXPORT_DATE: 2026-10-31T14:30:00
:EXPORT_DATE: <2026-10-31 Sat>
#+end_src

Zola's ~date~ field controls post ordering. Use ~updated~ for a last-modified timestamp.

*** Subtree dates

When ~org-log-done~ records completion time, switching a post to ~DONE~ inserts a ~CLOSED~ property:

#+begin_src org
,* DONE My post
CLOSED: [2026-10-31 Sat 14:10]
#+end_src

That timestamp becomes the post's ~date~. If ~CLOSED~ is absent, ~EXPORT_DATE~ is used, then the file-level ~#+date:~ keyword.

~SCHEDULED~ is an Org planning timestamp and is not a Zola publishing date. Front matter does not schedule posts; use your site's publishing workflow if you need that.

*** Last modified

Set an explicit updated date:

#+begin_src org
,#+zola_updated: 2026-11-02
#+end_src

Or enable automatic tracking:

#+begin_src org
,#+zola_auto_set_lastmod: t
#+end_src

When ~:LOGBOOK:~ state changes are available, they take precedence over the automatic value.

This exports as an inline image:

*** Heading anchors

Headings receive anchors in the exported Markdown. A custom ID can be set with ~:CUSTOM_ID:~:

#+begin_src org
,** Heading in a post
:PROPERTIES:
:CUSTOM_ID: heading-in-a-post
:END:
#+end_src

Zola's Markdown parser also understands heading attributes, so an explicit ID can appear on the heading:

#+begin_src markdown
### Heading in a post {#heading-in-a-post}
#+end_src

*** Anchor precedence

Ox-Zola derives heading anchors with this precedence:

1. Page or bundle name from ~EXPORT_FILE_NAME~
2. ~:CUSTOM_ID:~
3. A slug derived from the heading text
4. A short MD5-based fallback

The anchor precedence can be customized, including making Org ~:ID:~ properties take precedence.

*** Targets

Org ~<<target>>~ links become HTML anchors. Prefix a target name with a dot (~<<.bar>>~) when you need an unprefixed HTML anchor for cross-page links.

Links within a page use ordinary ~#anchor~ references; links across pages use Zola's ~@/~ path syntax. See [[/projects/ox-zola/content/internal-links/][Internal Links]].

#+begin_description
How ox-zola converts Org links to Zola's native path syntax.
#+end_description

#+begin_export html
{% raw %}
#+end_export

Ox-Zola converts Org links to Zola's native ~@/~ path syntax. Cross-references between posts, same-file heading links, external URLs, and file attachments all produce Zola-compatible Markdown.

*** Quick reference

| Org link | Zola output |
| ~[[*Some Heading]]~ | ~[Some Heading](#some-heading)~ |
| ~[[#custom-id]]~ | ~[custom-id](#custom-id)~ |
| ~[[id:uuid-here][Post]]~ | ~[Post](@/section/post.md)~ |
| ~[[file:other.org][Other]]~ | ~[Other](@/section/other.md)~ |
| ~[[file:other.org::*Heading][Link]]~ | ~[Link](@/section/other.md#heading)~ |
| ~[[https://example.com][Site]]~ | ~[Site](https://example.com)~ |
| ~[[file:image.png]]~ | ~![img](path/to/image.png)~ |

*** Same-file links

Links to headings within the same file use the standard ~#anchor~ format:

#+begin_src org
[[*Some Heading][link]]
[[#custom-id][link]]
#+end_src

They become:

#+begin_src markdown
[link](#some-heading)
[link](#custom-id)
#+end_src

*** Cross-file links

Links to other Org files become Zola ~@/~ paths. The prefix resolves from the Zola content root:

#+begin_src org
,#+zola_section: posts
[[file:other.org][other post]]
#+end_src

becomes:

#+begin_src markdown
[other post](@/posts/other.md)
#+end_src

Heading anchors and custom IDs are preserved:

#+begin_src org
[[file:other.org::*Some Heading][link]]
[[file:other.org::#custom-intro][introduction]]
#+end_src

#+begin_src markdown
[link](@/posts/other.md#some-heading)
[introduction](@/posts/other.md#custom-intro)
#+end_src

Org ~id:~ links resolve to the target file automatically:

#+begin_src org
[[id:abc123-def456-ghij][related post]]
#+end_src

*** Section detection

When the target file lives under the Zola ~content/~ directory, ox-zola extracts the correct section from the file's location. A file at:

#+begin_src text
~/mysite/content/tutorials/guide.org
#+end_src

with base directory ~~/mysite~ becomes:

#+begin_src text
@/tutorials/guide.md
#+end_src

If the section cannot be determined, the current document's section is used as a fallback.

*** External URLs and attachments

HTTP, HTTPS, FTP, and ~mailto:~ links pass through unchanged. Links to non-Org files such as images and PDFs are handled by the attachment rewrite mechanism.

*** Images and figures

Inline images use regular Markdown:

#+begin_src markdown
![alt](src)
#+end_src

For standalone figures, use raw HTML or a site-specific component.

*** No more relref

Internal references use Zola's native ~@/~ path syntax, so exported Markdown works directly with Zola.

*** Blocks handled directly

Some special blocks do not become shortcodes at all:

| Org block | Output |
| ~description~ | Sets the ~description~ field in TOML front matter and is removed from the body |
| ~details~ | Produces an HTML ~<details>~ element with an optional ~<summary>~ |
| ~aside~ | Produces an HTML ~<aside>~ element |

#+begin_src org
,#+begin_description

,#+end_description
#+end_src

#+begin_src org

Click to expand
---
Hidden content revealed on click.
,#+end_details
#+end_src

becomes:

#+begin_src html
<details>
<summary>Click to expand</summary>
Hidden content revealed on click.
</details>
#+end_src

*** Legacy shortcode output

Zola 0.22 and earlier used shortcode syntax for reusable blocks. Zola 0.23 uses components instead. For migration details, see [[/projects/ox-zola/getting-started/migration-from-ox-hugo/][Migrating from ox-hugo]].

*** Components in Zola 0.23

Define a component in ~templates/components/~:

#+begin_src jinja
{% component ui.callout(tone = "note") %}
<aside class="callout callout--{{ tone }}">{{ body | safe }}</aside>
{% endcomponent ui.callout %}
#+end_src

Call it from Markdown with a body:

#+begin_src markdown
{% <ui.callout tone="tip"> %}
The body still parses as **Markdown**.
{% </ui.callout> %}
#+end_src

Or use a self-closing component:

#+begin_src markdown
{{<ui.card title="A card" to="/projects/" />}}
#+end_src

Component arguments use quoted strings for text and ~{...}~ for non-string values.

*** Current behavior

For Zola 0.23 and newer:

- Use the ~description~, ~details~, and ~aside~ blocks, which produce front matter or plain HTML.
- Write component calls directly in Markdown when you need reusable markup.

The translation of these generated strings follows Org's export dictionary.

*** Zola multilingual sites

Zola's multilingual support is configured in ~config.toml~ with ~[languages]~, and content can be split per language with language-suffixed files such as ~_index.fr.md~ or ~page.fr.md~.

Ox-Zola's language handling is about the Org export, not a full translation management layer. For a multilingual site, decide how translated Org sources map to those language-specific content files, and verify the resulting paths with ~zola build~.

*** Scope

This page covers translated export strings and language metadata. It does not promise automatic translation of post bodies or automatic generation of every Zola language variant.

** Custom Front Matter
:PROPERTIES:
  :EXPORT_FILE_NAME: custom-front-matter
  :EXPORT_ZOLA_SECTION: projects/ox-zola/enhancements
  :EXPORT_ZOLA_WEIGHT: 30
  :EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :extra '((lead . "Use custom front matter when a Zola template needs a field that does not map to a standard Org keyword or property.") (toc . true) (adapted_from . "ox-hugo") (adapted_url . "https://ox-hugo.scripter.co/doc/custom-front-matter/"))
:END:

#+begin_description
Add template-specific fields to exported Zola front matter.
#+end_description

*** File-wide custom front matter

Use the ~ZOLA_CUSTOM_FRONT_MATTER~ keyword for the whole file:

#+begin_src org
,#+zola_custom_front_matter: :feature true
,#+zola_custom_front_matter: :show_toc false
#+end_src

*** Subtree custom front matter

Use ~EXPORT_ZOLA_CUSTOM_FRONT_MATTER~ for a post subtree, and append more values with the ~+~ property form:

#+begin_src org
,* My Post
:PROPERTIES:
:EXPORT_FILE_NAME: my-post
:EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :feature true
:EXPORT_ZOLA_CUSTOM_FRONT_MATTER+: :show_toc false
:END:
#+end_src

*** Values

The property accepts scalars, lists, and maps of scalar or list values:

#+begin_src org
:EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :feature true
:EXPORT_ZOLA_CUSTOM_FRONT_MATTER+: :animals '(dog cat "mountain gorilla")
:EXPORT_ZOLA_CUSTOM_FRONT_MATTER+: :versions '((emacs . "29.4") (zola . "0.23.4"))
#+end_src

This exports as TOML:

#+begin_src toml
feature = true
animals = ["dog", "cat", "mountain gorilla"]

[versions]
emacs = "29.4"
zola = "0.23.4"
#+end_src

For template data, put the custom values under ~extra~:

#+begin_src org
:EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :extra '((feature . true) (show_toc . false))
#+end_src

#+begin_src toml
[extra]
feature = true
show_toc = false
#+end_src

Maps of maps are not supported by this syntax. Keep custom front matter to the fields your Zola templates actually read.

** Replace Front Matter Keys
:PROPERTIES:
  :EXPORT_FILE_NAME: replace-front-matter-keys
  :EXPORT_ZOLA_SECTION: projects/ox-zola/enhancements
  :EXPORT_ZOLA_WEIGHT: 40
  :EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :extra '((lead . "Map exported front matter keys to the names your Zola template expects.") (toc . true) (adapted_from . "ox-hugo") (adapted_url . "https://ox-hugo.scripter.co/doc/replace-front-matter-keys/"))
:END:

#+begin_description
Rename or remove exported front matter keys without editing the Org source.
#+end_description

*** Syntax

Use the ~ZOLA_FRONT_MATTER_KEY_REPLACE~ keyword for the whole file:

#+begin_src org
,#+zola_front_matter_key_replace: oldkey>newkey
#+end_src

Or use the ~EXPORT_ZOLA_FRONT_MATTER_KEY_REPLACE~ subtree property:

#+begin_src org
,* My Post
:PROPERTIES:
:EXPORT_FILE_NAME: my-post
:EXPORT_ZOLA_FRONT_MATTER_KEY_REPLACE: oldkey>newkey
:END:
#+end_src

Multiple mappings are space-separated.

*** Rename a key

For example, a template that expects ~summary~ instead of ~description~:

#+begin_src org
,#+zola_front_matter_key_replace: description>summary
#+end_src

*** Swap tags and categories

#+begin_src org
,#+zola_front_matter_key_replace: tags>categories categories>tags
#+end_src

*** Remove a key

Use ~nil~ as the target to drop the key from the exported front matter:

#+begin_src org
,#+zola_front_matter_key_replace: aliases>nil
#+end_src

*** Rename authors

If an older template expects a singular ~author~ field:

#+begin_src org
,#+zola_front_matter_key_replace: authors>author
#+end_src

Only the exported front matter changes; the Org source keeps its original keywords and properties.

** Auto-export on Saving
:PROPERTIES:
  :EXPORT_FILE_NAME: auto-export-on-saving
  :EXPORT_ZOLA_SECTION: projects/ox-zola/enhancements
  :EXPORT_ZOLA_WEIGHT: 50
  :EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :extra '((lead . "Ox-Zola does not ship a dedicated auto-export mode; a buffer-local save hook is enough.") (toc . true) (adapted_from . "ox-hugo") (adapted_url . "https://ox-hugo.scripter.co/doc/auto-export-on-saving/"))
:END:

#+begin_description
Export the current Org post whenever you save it.
#+end_description

*** Define the export function

Put this in your Emacs configuration:

#+begin_src elisp
(defun my/ox-zola-export-on-save ()
  "Export the current Org post with ox-zola."
  (when (derived-mode-p 'org-mode)
    (ox-zola-export-wim-to-md)))
#+end_src

The function uses the normal WIM rules: it exports the current post subtree when point is in one, otherwise it exports the whole file.

*** Enable it for a project

Add a buffer-local hook through ~.dir-locals.el~:

#+begin_src elisp
((org-mode
  . ((eval . (add-hook 'after-save-hook
                       #'my/ox-zola-export-on-save
                       nil t)))))
#+end_src

The final ~t~ makes the hook buffer-local, so it does not run for every Org file in Emacs.

*** Enable it for one file

Add a file-local block at the end:

#+begin_src org
# Local Variables:
# eval: (add-hook 'after-save-hook #'my/ox-zola-export-on-save nil t)
# End:
#+end_src

To disable it for a file in an enabled project:

#+begin_src org
# Local Variables:
# eval: (remove-hook 'after-save-hook #'my/ox-zola-export-on-save t)
# End:
#+end_src

*** Live preview

Run Zola in the site root:

#+begin_src sh
zola serve
#+end_src

With the save hook active, saving the Org file exports the Markdown and the Zola server refreshes the preview.

** Org Capture Setup
:PROPERTIES:
  :EXPORT_FILE_NAME: org-capture-setup
  :EXPORT_ZOLA_SECTION: projects/ox-zola/enhancements
  :EXPORT_ZOLA_WEIGHT: 60
  :EXPORT_ZOLA_CUSTOM_FRONT_MATTER: :extra '((lead . "Generate the post heading and EXPORT_FILE_NAME automatically instead of typing them for every new entry.") (toc . true) (adapted_from . "ox-hugo") (adapted_url . "https://ox-hugo.scripter.co/doc/org-capture-setup/"))
:END:

#+begin_description
Create new Zola posts with an Org capture template.
#+end_description

*** Capture template

Define a template function and register it with ~org-capture-templates~:

#+begin_src elisp
(with-eval-after-load 'org-capture
  (defun my/ox-zola-capture-template ()
    "Return an `org-capture' template for a new Zola post."
    (let* ((title (read-from-minibuffer "Post Title: "))
           (fname (org-hugo-slug title)))
      (mapconcat #'identity
                 `(,(concat "* TODO " title)
                   ":PROPERTIES:"
                   ,(concat ":EXPORT_FILE_NAME: " fname)
                   ":END:"
                   "%?\n")
                 "\n")))

  (add-to-list 'org-capture-templates
               '("z" "Zola post" entry
                 (file+olp "all-posts.org" "Blog Ideas")
                 (function my/ox-zola-capture-template))))
#+end_src

~org-hugo-slug~ is inherited from the exporter dependency and turns the title into the post slug.

*** Page bundles

For a Zola page bundle, export ~index.md~ inside a named directory:

#+begin_src elisp
(defun my/ox-zola-bundle-capture-template ()
  "Return an `org-capture' template for a new Zola page bundle."
  (let* ((title (read-from-minibuffer "Post Title: "))
         (fname (org-hugo-slug title)))
    (mapconcat #'identity
               `(,(concat "* TODO " title)
                 ":PROPERTIES:"
                 ,(concat ":EXPORT_ZOLA_BUNDLE: " fname)
                 ":EXPORT_FILE_NAME: index"
                 ":END:"
                 "%?\n")
               "\n")))
#+end_src

Images and other assets can then live beside the exported ~index.md~.

*** Dates

If you log ~DONE~ timestamps, switch the new post to ~DONE~ and the ~CLOSED~ property supplies the date.

If you do not use ~org-log-done~, insert an explicit date in the template:

#+begin_src elisp
(let* ((date (format-time-string (org-time-stamp-format :long :inactive)
                                 (org-current-time)))
       (title (read-from-minibuffer "Post Title: "))
       (fname (org-hugo-slug title)))
  (mapconcat #'identity
             `(,(concat "* TODO " title)
               ":PROPERTIES:"
               ,(concat ":EXPORT_FILE_NAME: " fname)
               ,(concat ":EXPORT_DATE: " date)
               ":END:"
               "%?\n")
             "\n"))
#+end_src
